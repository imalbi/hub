# Hue (server)

- `src/integrations/hue/`: `contracts.ts` (zod: public state and commands; brightness is 1..100 percent publicly and 1..254 on the wire, `percentToRaw`/`rawToPercent` are the one conversion), `bluez.ts` (`createHueBluez`, the transport) and `module.ts` (`createHueInstance(transport)`, `createConfiguredHue`, `hueConfigSchema`). Setup and pairing are in the README next to them.
- The light is driven through BlueZ with `busctl --system --json=short call org.bluez ...` and the injected `ctx.run`/`deps.run`: no helper process, no second language. It finds the one paired device that lists the Hue GATT service (never a guess: two candidates and no `modules.hue.address` touches neither), never pairs, connects when needed, serializes writes, reads the light back after each, polls every 5 s only while a client watches (a power-off made through Echo is not pushed), retries at 1, 2, 5 then 30 s only while watched (unwatched, the next use retries: a lamp off at the wall must not cost a Bluetooth connect every 30 s), and never replays a command queued before a loss (`generation`).
- Failures reach clients only as a code (`unavailable` 503, `unsupported` 412, `timeout` 504, `failed` 500): no BlueZ text, path or address. `run` returns -1 for a timeout and a missing binary alike, so both read as `timeout`.
- Tests never touch the bus: `bluez.test.ts` runs the transport on `src/testing/fake-bluez.ts` (answers exactly the `busctl` calls the transport makes, in the JSON the tool prints, refuses everything else); `module*.test.ts` go through `buildServer` with the example module's fake light (`src/testing/fake-hue.ts`, `getFakeHue()` is the one made for the server under test; `fake.ts` adds `GET/POST /__fake/hue` for the e2e suite only).
- `pnpm smoke` checks only that `busctl --version` runs; it never reads or writes the light.
