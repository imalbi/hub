# Server (`@hub/server`)

Fastify 5 with tRPC 11 mounted at `/trpc`. `src/server.ts` builds the app (`buildServer()`), `src/index.ts` listens, `src/router.ts` holds `appRouter` and exports `type AppRouter` (the package entry point, consumed by the web app for types).

Notes about one module live in `AGENTS.md` inside that module's folder (`src/modules/<name>/` and the folders named below). Read the one for every module you touch.

`src/modules/audio/`, `src/modules/media/`, `src/modules/pomodoro/`, `src/modules/theme/`, `src/modules/layout/`, `src/modules/system/`, `src/modules/notes/` (`mail`, `sites`, `weather`, `study`, and `music` live in `hub-shared`; `Oggi` stays in the web shell).

## Where files go

```
src/
  index.ts, server.ts (buildServer), router.ts (appRouter), smoke.ts, and their tests (server-*.test.ts)
  core/      trpc, auth, origin, exec, live, config: what every module relies on
  db/        Drizzle schema and connection
  modules/<name>/  one folder per module: router, live hub, parsers, fixtures/ (devices holds pairing too)
  testing/   fake.ts (the e2e fake server) and fake-desktop.ts: test-only, never imported by index.ts
```

- Same flat rules as the web app: no barrels, no folder per file, a helper lives in the one module that uses it until a second one does.

## Node type stripping

The server runs `.ts` files directly with Node 24, so only erasable TypeScript is allowed:

- relative imports carry the `.ts` extension (`./router.ts`);
- type-only imports use `import type` or inline `type` (`verbatimModuleSyntax`);
- no `enum`, `namespace`, parameter properties or decorators (`erasableSyntaxOnly`); use `as const` objects and zod enums instead.

## Patterns

- Procedures take zod schemas as input (`.input(z.object(...))`); never trust a client value without one.
- Procedures live in module sub-routers (see "Action registry"), never as a flat list in `appRouter`.
- Plain functions and factories over classes. Return values, throw `TRPCError` for client-facing failures.
- External commands (`wpctl`, `playerctl`, `hyprctl`, `caelestia`) go through `ctx.run`, never `execFile` directly in a module. Their output is parsed defensively: missing devices and absent players are normal states, not crashes.
- Log with `app.log` / `req.log`, not `console.log`.

## Action registry

- never an input on `pomodoro.start`: the palette runs an input-less action at once, and an optional field turned "Avvia Pomodoro" into a form (`router-registry.test.ts` pins `start` without a schema); `core/focus-history.ts` exposes totals and completion notifications without giving modules the core database.
- deliberately not `z.literal`, because the command palette builds its form from the JSON Schema and cannot run a `const` field

The registry is the tRPC router: a module is a `defineModule` definition in `src/modules/<module>/module.ts` (see `docs/modules.md`), listed in `src/modules.ts`; `createAppRouter` mounts its sub-router (`router.ts` next to it) under its name. `health` is a root procedure, `devices` and `pairing` are two definitions from one folder. It exposes `state` (query), `onState` (subscription, see "Live state") and one mutation per action.

- Every mutation sets `.meta({ label, description, danger? })` (`ActionMeta` in `src/core/trpc.ts`): `label` is short Italian UI copy; `description` is English for an LLM ("Switch the default audio output to the next configured device"). `src/router.test.ts` requires both. Protected `registry.list` enumerates mutations and queries explicitly opted in with `label` and `description`, with `kind` and input JSON Schema generated with zod `io: "input"`; the palette filters for mutations. Opaque parsers remain listed but cannot run through generated forms.
- `pageOnly: true` in the meta keeps an action out of `registry.list` (so the palette) and out of MCP `tools/list` and `tools/call`: only its own page calls it (for example catalog `mail` sending and archiving: an MCP call runs as loopback, so `loopbackProcedure` alone would allow confirmation dialogs from agents).
- `core/registry.ts` removes zod JSON Schema's open index signature from its public type: tRPC serialization otherwise erases named fields into unknown, breaking inferred web forms. Runtime JSON Schema stays intact.
- The context is the core only: `{ db, run, config, files, client, remoteAddress, sockets }` (the last three are "Trust, pairing and the LAN"). Live hubs, the media art cache and pairing codes are built inside each module's `create` and reach its router by closure, never through `ctx`. `run` (`src/core/exec.ts`) is `execFile` with an argument array, 3 s default timeout and a 16 MB buffer (`pw-dump` alone is ~350 KB and grows with streams). It resolves `{ stdout, stderr, code }` and never throws: a non-zero exit, a missing binary and a timeout all come back as a code.
- `buildServer({ dbPath, deps?: { run, fetch }, config?, isLoopback?, webRoot?, moduleRoots?, exampleModules?, onlyModules? })` defaults to the real `run` and `fetch`, an empty config, the real loopback check, no static files and no discovered modules (`index.ts` passes the private root). `onlyModules` (folder names) limits discovery to those folders of every root, examples included; unset loads all and `index.ts` never sets it. A private module's tests pass its own name so a broken sibling cannot fail them (`server-modules.test.ts` pins it). Tests inject a fake `run` and a literal config, so they never touch the desktop or `config.local.json`; artwork tests inject `fetch` too.
- Parsing is pure and lives next to the router (`modules/audio/pipewire.ts`, `modules/media/playerctl.ts`): no I/O, zod at the boundary, unknown shapes skipped. Fixtures use generic device names only (`modules/audio/fixtures/pw-dump.json`).
- Action labels in registry metadata are short Italian copy. Desktop notifications keep their Italian text in one `copy.ts` per module (`modules/pomodoro/copy.ts`), never inline in the logic; private modules follow the same rule. Other server copy stays English. The only user-facing strings it returns to clients are values from the user's config (output labels); error messages are short English text that the web app replaces with its own copy.

## Live state

Deck tiles update by push, over the tRPC WebSocket (`wsLink` on the client). Polling stays the source of truth on purpose: media keys, the Caelestia popout and Spotify itself change state without going through Hub.

- `createLiveHub(read, intervalMs = 1000)` in `src/core/live.ts` is one poller shared by all subscribers: it reads only while someone is subscribed, compares the JSON with the last value and emits only on change. Pass `null` as the interval for push-only modules such as Pomodoro; it reads only on subscribe and notify. Reads never overlap (a tick or `notify()` that arrives mid-read triggers one more read afterwards, so a state read before a mutation finished is never the last word). A throwing `read` ends the subscriptions with that error instead of crashing the poller, but `read` should not throw on expected conditions (`run` never does).
- A hub's generation advances when the last subscriber leaves: in-flight success and error from that generation must be discarded even if a new subscriber has arrived. Queue a fresh read for the new generation; clearing `latest` alone is insufficient. Regression in `live.test.ts`.
- Each stateful module has `src/modules/<module>/live.ts` with `read<Module>State(run, ...)` (the one function behind both the `state` query and the hub) and `create<Module>Live(...)`. Each module's `create` builds its hubs once per server (`buildServer` calls every factory); they are not module-level singletons, so tests with a fake `run` never share state.
- `onState: protectedProcedure.subscription(({ signal }) => live.subscribe(signal))`, with `live` the hub the module's factory built. Always pass `signal`: the generator parks on `events.on(...)` and `return()` on an async generator that is mid-`await` is queued until the next event, so only the abort signal ends an idle subscription (and stops the timer when the last one leaves). The first yield is the current state, then every change; a new subscriber after an idle period reads fresh state instead of replaying a stale one.
- After a mutation succeeds: `void live.notify()`. It is a no-op without subscribers, so HTTP-level tests that assert the last `run` call (`calls.at(-1)`) are unaffected. The new state is pushed, the mutation does not return it.
- Measured on the real stack: a change made in Spotify reached the tile in 0.6 to 0.7 s (it waits for the next 1 s tick). playerctl lags the real change slightly after a mutation, so the immediate refresh can still read the old status; the next tick corrects it.
- Event sources (`pw-mon`, `playerctl --follow`) are a possible later optimisation, not a requirement.

## Config

`loadConfig()` in `src/core/config.ts` reads `$HUB_CONFIG`, default `config.local.json` at the repo root (resolved from `import.meta.url`, not the cwd). A missing file is an empty config; an invalid one throws a message naming the file and the field. Personal values (output labels, device name matches) live there, validated by the zod schema; `server.allowedOrigins` (array, default empty) adds page origins to the WebSocket allowlist; `config.example.json` is tracked with fake values and a test checks it parses. `src/index.ts` loads it and passes it to `buildServer`; procedures read `ctx.config`.

`HUB_PORT` moves both the server and the Vite proxy target, so a second dev stack can run next to one that is already on 4180. `server.host` (default `127.0.0.1`) is where `src/index.ts` listens; `assertCanListen(config)` refuses to start on a host the LAN can reach while `server.allowedOrigins` is empty, because every page would be refused, and its message says which origin to add (for example `http://<pc-name>.local:4180`).

## Settings (Impostazioni)

- An agent reading `settings.config` of a module without a schema gets `null`: nothing marks secrets in a raw slice, so only the PC sees it (`settings-router.test.ts`). `settings.core`/`saveCore` allow PC and agents to read/edit `mcp`, `jobs`, `backup` and `assistant`, never `server`; `core` redacts schema-marked secrets. `saveCore` merges only submitted fields from validated input, because Zod defaults would otherwise overwrite omitted stored values. Agent changes to `backup.dir` or `mcp.enabled` are refused, including human-confirmed agent calls. `mcp.client` is the global `claude`/`codex` choice, defaults to Claude for old configs, and is available to module procedures through `ctx.config`.
- `core/settings-router.ts` (`settings.*`, mounted by `createAppRouter` next to `registry`, not a `defineModule`) allows loopback and agent clients for `modules`, `core`, `saveCore`, `config({ module })`, `save` and `restore`; paired devices cannot call settings procedures. `modules` returns name, `kind` public/private, `status` on/off/failed and `hasConfig`. `modules.enabled` is the one protected query (names of modules that are on, so the deck can hide tiles). `settings` and `modules` are reserved names for discovery.
- **Off is a top-level `modulesOff: string[]`** in the config (`core/config-schema.ts`), never inside a module's slice: slices belong to their own, often strict, schemas. `createAppRouter` does not call `create` for an off public module and mounts `router({})` there (its paths answer `NOT_FOUND`; tRPC cannot answer for procedures nobody knows, owner decision 2026-11-09); `discoverModules` imports the definition but never creates it, opens no database and so leaves `modules/<name>.db` untouched. `core/module-states.ts` (`createModuleStates`) records every module at startup (`on`, `off`, `failed`); a failed one keeps its schema so settings can repair it, and its log line still carries the folder name only.
- **Schema for the form**: `settingsSchema` (optional field of `defineModule`) wins over `config`; a module whose config is absent, `z.undefined()`, `z.unknown()` or `z.any()` has no form, only the switch (`configSchemaOf`). Lavoro accepts any slice in `config` on purpose and names `profileSchema` in `settingsSchema`. `config` returns `z.toJSONSchema(schema, { io: 'input', unrepresentable: 'any' })` (`core/settings-config.ts`).
- **Secrets are write-only**: `.meta({ secret: true })` on a field (it survives into the JSON Schema as `"secret": true`; `secretPaths` finds them at any depth through objects and unions). `config` answers `{ set: true }` for a stored one and lists every secret path in `secrets`; `save` takes `{ set: true }` as "keep the stored value" and a string as a replacement. The value never leaves the server, and a test greps the whole response for it.
- **`save({ module, enabled?, value? })`** edits the raw JSON of the file (not the parsed config, so unknown keys survive), validates it with the full `configSchema` and, for a discovered module, with the module's own schema, and answers `{ ok: false, issues: [{ path, message }] }` (path relative to the module's slice) without touching anything, or writes: copy to `<file>.bak`, temporary file with the original mode (owner-only for a new one), rename. Omitting `enabled` preserves the module's current on/off state; only explicit `false` can disable it. `value` is `z.unknown().optional()`: zod 4 makes a bare `z.unknown()` key required, which broke the switch-only save (regression test in `settings.test.ts`). `restore` (danger, `confirmed: true`) swaps the file with `.bak` the same way, 404 without one and 412 when the backup does not parse with `configSchema` (a broken hand edit would otherwise leave the service failing on every restart).
- **Restart**: `ctx.restart()` (a function on the tRPC context, `save`, `saveCore` and `restore` call it) schedules `buildServer`'s `settings.onRestart` for when the response has finished (`res.raw.once('finish')`) and returns whether anything will restart. MCP calls schedule the callback after 200 ms instead (`server.ts`); tests must await the callback, not just the injected response. `index.ts` passes `onRestart` only under systemd (`INVOCATION_ID` set): `core/shutdown.ts` shares one idempotent `app.close()` with SIGTERM/SIGINT (module cleanup runs, a Lavoro collection is cancelled and recorded), with a 15 s deadline before systemd's 20 s stop limit, then exit code 75 and `hub.service` (`Restart=on-failure`) starts it again, no `deploy/` change. From a terminal (`pnpm dev`, `pnpm serve`) nobody would start it again, so a save only writes the file and answers `restarting: false` (the page says to restart Hub). The e2e fake restarts in place (`apps/e2e/AGENTS.md`).
- Settings `save`, `saveCore` and `restore` run through one promise chain (`serialized` in `core/settings-router.ts`): each is a read-modify-write of the same file, so two at once would lose one change. The temp file name also carries a `randomUUID()`.
- `settings.save`, `settings.saveCore`, `settings.restore` and the opted-in queries `settings.modules`, `settings.core`, `settings.config` are in `registry.list`. Agent saves and restores refuse the whole change when a secret or `.meta({ manual: true })` field changes, or pairing, devices or health is switched off; human approval does not override this rule. `server.host` is manual, and `core/settings-router.test.ts` walks all public and core `formSchema`s so any field matching `/command|page|terminal|file|dir|dirs|scheme|host|url/i` must carry `manual: true` (unless explicitly allowlisted as non-executable). Secrets inside objects, arrays and records are redacted and restored through the schema.
- Tests: `core/settings.test.ts` (paired device refused on every procedure, invalid save changes nothing, valid save keeps `.bak`/mode and asks for one restart, secrets, `settingsSchema`, switch-only save, no restart hook), `server-modules.test.ts` (`modulesOff` of a public module), `core/discovery.test.ts` (off discovered module and its db file, failed module and payload-free log). Never point a settings test at `config.local.json`: they use a `mkdtemp` file.

- `core/capabilities.ts` stages discovered-module registrations in a child registry until the factory validates; never publish partial services from a failed module. Declare dependency metadata in both the runtime definition and catalog manifest (see `docs/modules.md`). `/m/<name>` routes inherit the module scope's Host/Origin/auth guards; a route still owns any stricter authorization.

## Fake desktop and smoke check

- The script has no `--help`: an unknown flag is ignored and the digest runs for real (it happened once while planning this module).

- `src/testing/fake-desktop.ts` (`createFakeDesktop({ notifications? })`) is the one fake `Run`: the `pw-dump` fixture with a default sink that `wpctl set-default <id>` moves, sink volume/mute and mic mute simulation for `wpctl get-volume`, `set-volume` and `set-mute`, and one track (`Artist` / `Title`) whose status flips on `playerctl play-pause`. `notify-send --app-name Hub -- <title> <body>` is accepted only with `--` before positional arguments (4-arg calls without `--` are refused) and recorded in the optional notifications array without invoking a binary. Anything else, including an unknown sink id, is answered with a non-zero code and no state change, so it can never reach a real binary (`fake-desktop.test.ts`). Each call makes a new desktop; tests and `fake.ts` share this module, do not write a second fake.
- `src/testing/fake.ts` is the server for the e2e suite: `buildServer` with that fake, an in-memory DB, a fixture config (outputs `Cuffie` and `Casse`, the e2e Vite origins on the allowlist) and an `isLoopback` that treats a request with `Host: localhost:*` as the PC and any other host as a phone. Loopback, port `HUB_PORT` (default 4190). Never point it at a real config. It owns a config file in `HUB_E2E_TMP` for Impostazioni and a file database there (a restart must keep paired devices and module data); `settings.onRestart` closes the server, waits `HUB_E2E_RESTART_MS` (default 1500) and builds it again from the fixture config plus the file (top-level keys of the file replace the fixture's), so no process ever exits.
- `src/smoke.ts` (`pnpm smoke`): `runSmoke(run)` checks `wpctl --help` lists `set-default` (wpctl has no `--version`), `wpctl get-volume` parses sink volume, `playerctl --version`, `pw-dump` through `parsePwDump` (needs a sink and a default sink) and `playerctl metadata` through `parseMediaState` ("No players found" is ok), plus `notify-send --help` for the app-name option (never sends a notification), `pw-play --version`, `systemctl --version`, `caelestia shell -s` (the lock IPC target is listed; nothing is called) and `caelestia toggle --help`, `hyprctl monitors all -j` through `parseMonitorList` (read only; never the toggle), and the powerstat dir through the real parser when `system.powerstatDir` is configured. Read-only by test (`smoke.test.ts` lists the commands it runs); the report says ok, missing or unparseable per check and the exit code is non-zero if any is not ok. `run` returns -1 for both a missing binary and a timeout.
- Smoke also checks `playerctl --player=mpv status` (no player is OK): the `media` module prefers mpv while it is playing or paused (`modules/media/preference.ts`).

## Trust, pairing and the LAN

- **Who is calling** (`resolveClient` in `src/core/auth.ts`, run by `createContext` in `src/server.ts`): `loopback` when the TCP peer address is `127.0.0.1`, `::1` or `::ffff:127.0.0.1` (the PC itself); `device` when `Authorization: Bearer <token>` (HTTP) or the `token` connection param (WebSocket) hashes to a row of `devices`; otherwise `anonymous`. `X-Forwarded-For` is never read and Fastify `trustProxy` stays off: any LAN client can send that header. A `127.0.0.1` peer is always the PC, which is why Vite must never be exposed (its proxy makes everything look like loopback) and the LAN is served by Fastify itself.
- **Procedure kinds** (`src/core/trpc.ts`): `publicProcedure` is for `pairing.redeem` only; `protectedProcedure` (PC, paired device or agent, `UNAUTHORIZED` otherwise) is the default for everything, `health` and every `onState` subscription included; `loopbackProcedure` (PC only, `FORBIDDEN` for a device) is for `pairing.createCode` and `devices.*`. Pick the kind first when adding a procedure; a new one is protected unless there is a reason.
- **WebSocket auth happens once per connection**, when the adapter calls `createContext` with `info.connectionParams` (the client sets `?connectionParams=1` and sends them as its first message). Revocation and expiry must also close already-open sockets: `src/core/auth.ts` keeps `sockets` (device id to open sockets, filled in `createContext`) and `devices.revoke` closes them with code 4401. Tracking takes the token expiry; timers recheck at Node's maximum delay (longer delays clamp to 1 ms). `protectedProcedure` also checks expiry on every call. The adapter passes the `ws` socket where the typings say `FastifyReply`, hence the `isSocket` guard.
- **Pairing** (`modules/devices`: `codes.ts`, `pairing-router.ts`): `createCode` makes one random 6-digit code, valid 120 s, single use, kept in memory (`codes.ts`, one active code, a new one replaces it). `redeem({ code, deviceName })` compares in constant time and returns the token once; a wrong code is `BAD_REQUEST`, 5 wrong codes per IPv4 address / IPv6 `/64` prefix (`bucketAddress`) per minute lock that bucket out with 429 for the rest of the minute (even for the right code), and 10 wrong attempts across all callers burn the active code. The token is 32 random bytes in base64url; only its SHA-256 is stored (`devices` table: `id`, `name`, `token_hash` unique, `created_at`, `last_seen_at`, refreshed at most once a minute, nullable `last_seen_ip` from the TCP peer, updated immediately when it changes). `server.deviceTokenTtlDays` (integer 1-365, default 90) expires tokens from `created_at`, including existing pairings; old rows retain a null IP until access. `devices.list` derives `expiresAt` from the current config. Revoking deletes the row.
- **Approval preserves device restrictions**: `loopbackProcedure` and `agentOrLoopbackProcedure` inherit `deviceForbidden` metadata. `agent-action.ts` copies it into a pending confirmation; `confirmations.confirm` requires the approving `Client` and refuses a device before running or consuming a PC-only request. Never elevate a phone approval without checking this flag.
- **The PC switch is an option, not a mode**: `buildServer({ isLoopback })` overrides its default, `isLoopbackPeer` (`core/auth.ts`). Only `src/testing/fake.ts` (the e2e server, which tells the desk page and the deck page apart by `Host`) and tests pass it; `src/index.ts` never does. `core/auth.test.ts` builds the server without the option and pins that `127.0.0.1` is the PC and a LAN address with a forged `X-Forwarded-For` is not.
- **Static app**: `buildServer({ webRoot })` serves `apps/web/dist` with `@fastify/static` and answers extensionless GETs outside `/trpc` with `index.html` (the `/deck` and `/desk` routes); a missing file with an extension, and anything not GET, is a 404. `src/index.ts` passes `webRoot` only when `dist/index.html` exists. `pnpm serve` (root) builds the web app and starts the server.
- **Trying `pnpm serve` without touching real data**: `HUB_DB=<scratch>.db HUB_CONFIG=<missing file> pnpm serve` uses a scratch database and an empty config (the real ones are `~/.local/state/hub/hub.db` and `config.local.json`); pairing writes a device row, so never do it against the real database. The page origin `http://127.0.0.1:4180` is already on the allowlist.

## Database: Drizzle v1 + SQLite (`node:sqlite`)

- One local file, no database server: single user, single writer, small data. Postgres would only earn its place if several machines wrote to the same store.
- Path: `$HUB_DB`, default `~/.local/state/hub/hub.db` (outside the repo). WAL mode and foreign keys are set on open.
- `openDb()` in `src/db/index.ts` applies pending migrations synchronously at startup, before the server listens. Tests use `openDb(':memory:')`. It is `openDatabase(path, migrationsFolder)` with the tracked `drizzle/` folder; the same function opens a module's file (see "Core and module databases"), and closes the handle again when a migration throws.
- Primary keys: `integer` autoincrement for rows that live and die on this machine (sessions, devices, themes). A table whose ids leave it (synced to another store, shown to an agent or a third party, created offline on a device) uses a text UUID from `crypto.randomUUID()` instead, decided when that table is planned.
- Schema in `src/db/schema.ts`, explicit snake_case column names (`integer('started_at', ...)`). Timestamps are `integer` with `mode: 'timestamp_ms'`, booleans `integer` with `mode: 'boolean'`.
- Change the schema, then `pnpm --filter @hub/server db:generate` and commit the folder it writes under `drizzle/`. Never edit a migration that has already run; add a new one. `db:studio` opens Drizzle Studio.
- Drizzle is v1 (release candidate, `drizzle-orm@rc`): the `node-sqlite` driver only exists there. Check the installed typings in `node_modules/drizzle-orm/` before trusting 0.x examples from the web. Relational queries use the v2 object syntax (`where: { id: 1 }`), as in the Efebia projects.
- The core db reaches procedures through the tRPC context (`ctx.db`), never as a module-level singleton.

### Core and module databases

- Public modules declaring `migrations` receive a separate database via `createAppRouter`, at the same `moduleDbPath` as discovered modules; module cleanup runs before database closure.

- Two kinds of file. The **core** database (`hub.db`) belongs to the public modules: devices, layouts, themes, Pomodoro history. A **module** database belongs to one discovered module that declared `migrations` in `defineModule`: `<dirname(dbPath)>/modules/<name>.db`, opened by `discoverModules` through `openDatabase(moduleDbPath(dbPath, name), migrations)`, `:memory:` when the core is. It reaches the module only as `deps.db` in its factory, by closure; `ctx.db` is always the core one, and a module's procedures never read it.
- Isolation is by type and by construction: `discoverModules` takes `DiscoveredDeps` (no `db`), `buildServer` passes it a separate object from the public `ModuleDeps`, and a discovered definition with `coreDb` is refused. `defineModule` types `db` from the options: `migrations` gives it, `coreDb: true` gives the core one, neither gives none (`server-modules-db.test.ts` has a `@ts-expect-error` for that). `pomodoro` and `theme` are the two public modules that declare `coreDb`.
- Failures stay local: the database is opened after the name and zone checks and before `create`; if opening, `create` or the instance check throws, the module's `close` and the database handle are closed and the module is skipped.
- Close order: Fastify runs `onClose` hooks last in, first out, so the database hook is registered before the module's `close` and runs after it (a module can still write in `close`; the same reason the core database hook is registered first in `buildServer`).
- Generating a module's migrations is in `docs/modules.md`; `pnpm --filter @hub/server db:generate` is for the core only.
- drizzle names a foreign key `fk_<table>_<column>_<table>_<column>_fk`, which the private-data guard reads as a token. A new migration with a foreign key gets `-- guard-private: allow generated foreign key name` at the end of that line, before its first run (music `playlist_songs`, 23f). `pnpm check` misses it while the folder is untracked; the guard sees it after `git add`.

## HTML for modules

- `@hub/server` itself has no `linkedom` dependency (`linkedom` was extracted to per-module `package.json` + `pnpm-lock.yaml` in step 103; see `docs/modules.md`). Modules needing DOM parsing install `linkedom` in their own folder and import `{ parseHTML } from 'linkedom'` directly.
- The server tsconfig has no DOM lib, while modules are typechecked with the DOM lib (`scripts/tsconfig.modules.json`), where `parseHTML(...).document` is a plain `Document`. Do not import linkedom's `DOMParser`: it returns linkedom's own `HTMLDocument`, which is not assignable to `Document`.
- linkedom's parser is lenient and not spec-exact on malformed markup. Code that must be safe on hostile input builds its output from an allowlist and escaped text instead of editing the parsed tree, and its tests assert properties (only allowlisted tags, no attribute) over a list of hostile strings rather than exact trees.

## Security invariants

- `core/trpc.ts` explicitly sets `isDev: false` and an `errorFormatter` that replaces unexpected `INTERNAL_SERVER_ERROR` causes (`error.cause !== undefined`) with `'Internal server error'`, never exposing stacks or source paths regardless of `NODE_ENV` or the service environment.
- Global `onRequest` `Host` validation (`isAllowedHost` in `core/origin.ts`) rejects missing, multi-valued, malformed, obfuscated or foreign `Host` headers with `421` across HTTP routes and WebSocket upgrades.
- `@fastify/helmet` sets global security headers (`X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`, CSP without `'unsafe-eval'`, `'unsafe-inline'` scripts, `upgrade-insecure-requests`, or `hsts` so plain-HTTP LAN `/deck` keeps working).
- HTTP `/trpc` runs in its own scoped plugin (`server.ts`) rejecting present non-allowlisted `Origin` headers with `403`, non-`application/json` non-GET/HEAD/OPTIONS requests with `415`, and removing `multipart/form-data` from that scope (`registerFiles` keeps its own scope). `@fastify/websocket` caps `maxPayload` at 1 MiB.
- `isAllowedOrigin` (`core/origin.ts`) rejects origins longer than 256 chars and strips trailing slashes linearly; `DEV_ORIGINS` includes `http://localhost:4180`.
- `serializeRequest` (`server.ts`) strips query strings from request logs and WebSocket refusal logs omit query strings and raw untrusted `Origin` values.
- `core/files.ts` enforces 50 entries and 100 MiB total quota (`413` on `/files`), and `GET /files/:id` answers generic `500` on read/open failures without OS paths. `discoverModules` reserves `'jobs'`; `calendar.range` caps spans at 400 days (`series.ts` caps expansion at 401 days); `assistant.warm`/`ask` use `loopbackProcedure` (`FORBIDDEN` for paired devices, preserving tokens in `authLink`).
- WebSocket upgrades (tRPC subscriptions, the deck) check `Origin` against an allowlist before the connection is bound: CORS does not cover WebSockets, so any page open in the browser could otherwise drive the desktop through `localhost`. It lives in `src/server.ts`: `verifyClient` (the 2-argument form, the only one that can answer 403) in the `@fastify/websocket` options, with `isAllowedOrigin` from `src/core/origin.ts`. A missing `Origin` is refused too; a refused upgrade is logged at `warn`. The allowlist is `DEV_ORIGINS` (Vite on 5173, the server on 4180) plus `config.server.allowedOrigins`; trailing slash and case are ignored. Vite on another port (it moves to 5174 when 5173 is taken) is refused until its origin is in the config. HTTP CORS is not configured yet; when it is, it reads the same allowlist.
- `/files` (`core/file-routes.ts`) refuses a request whose `Origin` is present and off the same allowlist: a multipart POST is a CORS simple request with no preflight, so without it any page open on the PC could upload from loopback. tRPC is covered by its `application/json` requirement (415 otherwise). `server-files.test.ts` pins both.
- Fastify `routerOptions.maxParamLength` is 5000 (`server.ts`): tRPC puts a whole HTTP batch in one path parameter, and the default 100 answered 414 once a page batched about 8 calls (Lavoro's initial state broke; `server-batch.test.ts`).
- `@fastify/websocket` must be registered before the tRPC plugin (which gets `useWSS: true` and `keepAlive`), or the WebSocket route is not recognised.
- Who may call what is decided in the tRPC context and three procedure kinds, never inside a procedure body: see "Trust, pairing and the LAN".
- Every LLM call goes through the budget/rate-limit gate in `core/llm-gate.ts` before hitting the provider, so a stuck button or a loop cannot burn the quota.
- `index.ts` passes the shared `llmGate` into `buildServer`, which attaches its SQLite usage store before module discovery; core assistant, brief and catalog callers share that queue. Fake servers get isolated gates so closing one database cannot invalidate another server's counter.
- `core/brief.ts` persists the daily attempt before provider calls, including unavailable attempts; only explicit refresh retries that day. Keep warnings payload-free and advance its cursor only on success.
- `llmGate(cap, call, { minIntervalMs, counted })`: `counted: false` (the catalog `lavoro` mail check) queues and times out like any call but neither meets the cap nor adds to the daily count the Parere shares, so reading a week of mail cannot starve it. `core/capabilities.ts` defines the typed `MailCapability` (`listThreadEntries`, `readMessageText`, `threadOf`, `accounts`) provided by the catalog `mail` module via `capabilities`.
- Destructive actions (`danger: true` in the meta) are refused with `PRECONDITION_FAILED` unless the input carries `confirmed: true`: `confirmDanger` in `core/trpc.ts` is middleware on the base procedure, so it covers every kind and runs before input validation. Each danger mutation also declares `confirmed: z.literal(true)` so the typed client must pass it; web controls use `HoldButton` or `HoldTile`. `src/router.test.ts` lists every danger mutation and checks each is refused without the flag and runs with it.

## Tests

- `node:test` runs `t.after` hooks in registration order. Register the server's close before removing its temp folder, or in one hook (`await app.close(); await rm(...)`): the study tests removed the folder first and failed with ENOTEMPTY under load while the state writer still wrote.

`node:test` + `node:assert/strict`, files next to the code as `*.test.ts`. HTTP-level tests use `buildServer().inject(...)`, no real port. Anything that would call a system binary gets its runner injected so tests never touch the real desktop.

- A POST through `inject` needs `content-type: application/json` (and a body such as `{}`), or tRPC answers 415. The tRPC client always sends it.
- `appRouter._def.procedures` is a flat path-to-procedure map at runtime but typed as the nested tree: widen with `Object.entries<unknown>` and a type guard (see `src/router.test.ts`).
- File-backed module databases are tested in `src/server-modules-db.test.ts`: fixtures in a `mkdtemp` directory (module folders with hand-written `migration.sql`, the core database in a sibling `state/` folder), removed with `t.after`; the e2e fake and every other test use `:memory:`.
- WebSocket tests use a real server on `listen({ port: 0 })` (`const port = Number(new URL(await app.listen(...)).port)`). Node's global `WebSocket` accepts `{ headers: { Origin } }` and sends no `Origin` by default; `src/server-live.test.ts` drives the tRPC wire protocol with it (`{ id, method: 'subscription', params: { path } }`, answers `started` then `data`) against the shared fake desktop; `src/core/origin-ws.test.ts` sends raw upgrades with `node:http` to read the status code. `tsconfig.json` sets `lib: ["es2023"]` on purpose: without it TypeScript pulls in the DOM typings, whose `WebSocket` constructor has no `headers` option. `@types/ws` is not importable from this package, so the `verifyClient` callback is annotated structurally.
- A discovered module is built by its default export alone. To inject fakes (a source registry, a clock) it also exports a factory (`createXModule(options)`, the default export being `createXModule()`), and its test writes a one-line `server.ts` calling the factory into a `mkdtemp` root, as `server-modules.test.ts` does for its fixtures, reading the fakes from a small shared object the test fills in before `buildServer`.
- Hub tests use `mock.timers.enable({ apis: ['setInterval'] })` and flush promises with `setImmediate` from `node:timers/promises` (not mocked); end a parked subscription with its `AbortController`, not `return()` (see "Live state").
- Auth tests: `core/auth.test.ts` (HTTP through `inject({ remoteAddress })`, pairing, hash storage, last seen with `mock.timers.enable({ apis: ['Date'] })`), `modules/devices/codes.test.ts` (the store, expiry and rate limit on a mocked `Date`), `core/auth-ws.test.ts` (a real socket with connection params; its `isLoopback` option says the PC only by a header, so a socket from `127.0.0.1` can act as a phone). `server-static.test.ts` builds the server on a temp directory. `inject` answers `127.0.0.1` unless `remoteAddress` is given; zod 4 needs `z.unknown().optional()` for a void result in a response envelope.
- Never call a real mutation (`audio.cycleOutput`, `media.playPause`) against the live system to check it: they change the user's audio. Drive them through a server built with `createFakeDesktop()`.

## Backup

- `core/backup.ts` copies the core database and each module database once per local day with `node:sqlite` `backup()` (never `copyFile` on a live file). Handles reach it without a second open: `buildServer` passes the core `db.$client`, `createAppRouter` (public modules) and `discoverModules` (`onDb`) call `backup.add(name, handle)`. A module named `hub` cannot overwrite the core copy: the core goes to `hub.db`, modules to `modules/<name>.db`.
- The hourly check starts only with `buildServer({ autoBackup: true })` (`index.ts`); tests and the e2e fake call `backup.run`. Its timer is `unref`'d and stopped by an `onClose` hook. `backup.close` is the last `onClose` of the plugin scope, so it runs before the module and core handles close, and it waits for a start check that has not begun its copy yet as well as for a copy in progress (`backup.test.ts`, the closing test). Answers carry a fixed failure sentence, never a path or driver message. `backup.state` and `backup.run` are `agentOrLoopbackProcedure`: a paired device gets `FORBIDDEN`, an anonymous peer `UNAUTHORIZED`. See `docs/backup.md`.

## Jobs

- `core/jobs.ts` runs registry jobs with `jobs.maxConcurrent` (default 2), a 10-minute default timeout and a fakeable `StreamSpawn` from `core/exec.ts`; commands use a binary plus argument array, never a shell. A job action uses `jobProcedure.meta({ label, description, job: true, timeoutMs? })` and returns `ctx.startJob(binary, args)`; only registered actions choose commands.
- `jobs.list/onUpdate/output/onOutput/cancel` are protected. Cancellation is `danger: true` and requires `confirmed: true`. The core SQLite history retains 100 records and 50 output lines per record; the live runner keeps 500 lines per job. Shutdown kills and records active and queued jobs as cancelled, including in-process tracked jobs.

- Discovered modules receive only `deps.trackJob(action, { onCancel? })`: tracked work shares bounded output/history and cancellation, without occupying process slots or exposing `start`. `core/module.ts` is imported by browser code: keep job types as type-only imports and the no-op fallback browser-safe.

## MCP agents

- `core/mcp.ts` serves stateless Streamable HTTP at `/mcp` when `mcp.enabled` is true. An absent Origin is accepted; a present Origin must match the WebSocket allowlist. LAN requests need an agent bearer token. `core/agents-router.ts` issues it once and stores its SHA-256 hash.
- Tool discovery uses `registry.list`; calls run through tRPC with client kind `agent`. `confirmDanger` never accepts an agent confirmation. `core/confirmations.ts` keeps pending dangerous calls for two minutes, refuses requests with no subscribed desk or deck, and executes only after a human hold. `confirmations.status` reports the outcome.
- `core/confirmations.ts` deletes finished entries (confirmed, failed, denied, expired) 10 minutes after they finished, on any sweep and by a timer; `confirmations.status` for a gone id answers `{ state: 'expired' }` (a wrong agent on a live entry is still NOT_FOUND). Entries hold the `run` closure, so keeping them leaks.
- `core/agent-audit.ts` masks guard-detected values and retains the latest 500 calls in `agent_calls`; avoid logging raw tool input or output elsewhere. `result` keeps only the first 2 KB of the masked JSON plus ` …[truncated, N chars]` (the column stays text, no migration).
- Agents exist only on `/mcp`: a tRPC HTTP call with an agent token from the LAN is `anonymous` and from the PC is `loopback`, so a test of an agent-only path goes through `tools/call` or `resources/read`. Resources are the queries with no input that have an `on<Name>` sibling (`state`), so a module's `state` is what an agent reads; a procedure that is `agentOrLoopbackProcedure` but not a resource is reachable by agents only as a tool.
- `meta.danger` is static: a mutation that is dangerous only for some inputs (Lavoro `setFlag` with `flag: 'applied', value: false`) cannot use it. It takes `confirmed: z.literal(true).optional()`, throws `PRECONDITION_FAILED` without it, and `FORBIDDEN` for an agent, so the agent path is the always-`danger` `deleteApplication`.
- A paired phone gets no names: Sites `state` is agent-or-PC only (the deck reads `configured`, a boolean), catalog `mail` gives a non-PC caller `#1`, `#2` and empty labels plus `latest: []` (`forClient` in `router.ts`, only unread counts stay for the deck), and `notes/router.ts` strips `about` to `null` on `open`/`onOpen` and answers `[]` on `about` for paired `device` callers (`study` and `calendar` remain device-readable per Step 45).
- `core/pinned-http.ts` (`pinnedRequest`, `PinnedHttpError`, re-exported via `core/module.ts`) executes HTTP(S) GETs strictly against a pre-validated DNS IP target without redirects or streaming overflow, preventing TOCTOU DNS rebinding.
- `core/assistant.ts` uses `callAgentAction` shared with MCP. Strip model `confirmed`, require exact offered names, and refuse a near-full `num_ctx`; assistant calls are loopback-only and disabled by default. `core/ollama.ts` owns the loopback chat transport. `assistant.warm` (loopback, pageOnly) loads the model when the palette opens: an empty `messages` list only loads it, with the same `num_ctx` as `ask` or Ollama reloads it; both send `keep_alive: 30m`.
- Optional `assistant.decisionModel` invokes System One once per executable turn through `llmGate` with front priority. A high risk result adds confirmation through `callAgentAction`'s `forceConfirm`; lower risks and provider failures retain all static danger/manual/denied-prefix checks. `core/ollama.ts` validates typed choice/noul/score answers and masks provider failures. Warm loads only chat, through the queue; warnings never include provider text or action input.
- `core/catalog.ts`, `core/catalog-manifest.ts`, `core/catalog-router.ts`: Git module catalog backend (`module_sources`, `installed_modules`, `catalog_state`). Every `catalog.*` procedure uses `loopbackProcedure` and `pageOnly: true`, and `catalog` is mounted only on the outer `AppRouter` (never in `registered`), so paired devices, MCP agents, `registry.list`, palette, and assistant never see or invoke it. Git URLs are restricted to `https://`, `git@host:path`, and `ssh://git@...`; `git` runs with `-c core.hooksPath=/dev/null -c core.symlinks=false -c submodule.recurse=false`, `--`, and `GIT_TERMINAL_PROMPT=0` without shell strings or package installs. Manifest `path` validation rejects traversal and any symlink in the module tree before atomic staging into `modules.installed/<name>/`; `modules.local/` wins on name collisions, module removal preserves `<dbDir>/modules/<name>.db`, and `catalog.applyChanges` runs `catalog.build` through `jobs` (clearing `pendingApply` and invoking `onRestart` only on exit code 0). <!-- guard-private: allow Repository-local module directory -->

- `core/catalog-manifest.ts` preserves missing regular `*.local.*` files from the installed tree before `prepare` and the atomic swap; incoming files win. Local traversal uses `lstat`, skips symlinks and dependency/Git folders, and must not create empty parent directories that could change prepare behavior.
- `core/discovery.ts` reserves earlier roots' folders and declared names before module creation: a broken local override must not start an installed fallback. `core/catalog.ts` serializes apply with mutations and keeps its build lock until the watcher finishes updating pending state and requesting restart.
