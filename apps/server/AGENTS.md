# Server (`@hub/server`)

Fastify 5 with tRPC 11 mounted at `/trpc`. `src/server.ts` builds the app (`buildServer()`), `src/index.ts` listens, `src/router.ts` holds `appRouter` and exports `type AppRouter` (the package entry point, consumed by the web app for types).

## Where files go

```
src/
  index.ts, server.ts (buildServer), router.ts (appRouter), smoke.ts, and their tests (server-*.test.ts)
  core/      trpc, auth, origin, exec, live, config: what every module relies on
  db/        Drizzle schema and connection
  modules/<name>/  one folder per module: router, live hub, parsers, fixtures/ (devices holds pairing too)
  testing/   fake.ts (the e2e fake server) and fake-desktop.ts: test-only, never imported by index.ts
```

- Same flat rules as the web app: no barrels, no folder per file, a helper lives in the one module that uses it until a second one does.

## Node type stripping

The server runs `.ts` files directly with Node 24, so only erasable TypeScript is allowed:

- relative imports carry the `.ts` extension (`./router.ts`);
- type-only imports use `import type` or inline `type` (`verbatimModuleSyntax`);
- no `enum`, `namespace`, parameter properties or decorators (`erasableSyntaxOnly`); use `as const` objects and zod enums instead.

## Patterns

- Weather (`modules/weather`): optional `{ name, latitude, longitude }` config; Open-Meteo forecast is cached for 30 minutes and the last result becomes stale on failure. Geocoding search is loopback-only. Tests inject `fetch` and fictional locations.

- Procedures take zod schemas as input (`.input(z.object(...))`); never trust a client value without one.
- Procedures live in module sub-routers (see "Action registry"), never as a flat list in `appRouter`.
- Plain functions and factories over classes. Return values, throw `TRPCError` for client-facing failures.
- External commands (`wpctl`, `playerctl`, `hyprctl`, `caelestia`) go through `ctx.run`, never `execFile` directly in a module. Their output is parsed defensively: missing devices and absent players are normal states, not crashes.
- Log with `app.log` / `req.log`, not `console.log`.

## Action registry

The registry is the tRPC router: a module is a `defineModule` definition in `src/modules/<module>/module.ts` (see `docs/modules.md`), listed in `src/modules.ts`; `createAppRouter` mounts its sub-router (`router.ts` next to it) under its name. `health` is a root procedure, `devices` and `pairing` are two definitions from one folder. It exposes `state` (query), `onState` (subscription, see "Live state") and one mutation per action.

- Every mutation sets `.meta({ label, description, danger? })` (`ActionMeta` in `src/core/trpc.ts`): `label` is short Italian UI copy; `description` is English for an LLM ("Switch the default audio output to the next configured device"). `src/router.test.ts` requires both. Protected `registry.list` enumerates mutations and queries explicitly opted in with `label` and `description`, with `kind` and input JSON Schema generated with zod `io: "input"`; the palette filters for mutations. Opaque parsers remain listed but cannot run through generated forms.
- `pageOnly: true` in the meta keeps an action out of `registry.list` (so the palette) and out of MCP `tools/list` and `tools/call`: only its own page calls it. Mail sending and archiving use it (step 39 review): plan 39 says sending never comes from an agent, and an MCP call runs as loopback, so `loopbackProcedure` alone did not stop it; the owner's confirmation dialog would have let an agent send. Regression in `modules/mail/router-send.test.ts`.
- `core/registry.ts` removes zod JSON Schema's open index signature from its public type: tRPC serialization otherwise erases named fields into unknown, breaking inferred web forms. Runtime JSON Schema stays intact.
- The context is the core only: `{ db, run, config, files, client, remoteAddress, sockets }` (the last three are "Trust, pairing and the LAN"). Live hubs, the media art cache and pairing codes are built inside each module's `create` and reach its router by closure, never through `ctx`. `run` (`src/core/exec.ts`) is `execFile` with an argument array, 3 s default timeout and a 16 MB buffer (`pw-dump` alone is ~350 KB and grows with streams). It resolves `{ stdout, stderr, code }` and never throws: a non-zero exit, a missing binary and a timeout all come back as a code.
- `buildServer({ dbPath, deps?: { run, fetch }, config?, isLoopback?, webRoot?, moduleRoots?, exampleModules?, onlyModules? })` defaults to the real `run` and `fetch`, an empty config, the real loopback check, no static files and no discovered modules (`index.ts` passes the private root). `onlyModules` (folder names) limits discovery to those folders of every root, examples included; unset loads all and `index.ts` never sets it. A private module's tests pass its own name so a broken sibling cannot fail them (`server-modules.test.ts` pins it). Tests inject a fake `run` and a literal config, so they never touch the desktop or `config.local.json`; artwork tests inject `fetch` too.
- Parsing is pure and lives next to the router (`modules/audio/pipewire.ts`, `modules/media/playerctl.ts`): no I/O, zod at the boundary, unknown shapes skipped. Fixtures use generic device names only (`modules/audio/fixtures/pw-dump.json`).
- Action labels in registry metadata are short Italian copy. Desktop notifications keep their Italian text in one `copy.ts` per module (`modules/pomodoro/copy.ts`), never inline in the logic; private modules follow the same rule. Other server copy stays English. The only user-facing strings it returns to clients are values from the user's config (output labels); error messages are short English text that the web app replaces with its own copy.
- PipeWire: state from `pw-dump` JSON (sinks are `Audio/Sink` nodes, the default is `default.audio.sink` in the metadata), switch with `wpctl set-default <id>`. Volume and mute read through `wpctl get-volume @DEFAULT_AUDIO_SINK@` and `@DEFAULT_AUDIO_SOURCE@` (state gains `volume` clamped to 0..1, `muted` boolean, `micMuted` boolean; missing source returns `micMuted: false`). Mutations: `audio.setVolume({ value })` (clamped 0..1), `audio.stepVolume({ direction: 'up' | 'down' })` (steps 5%, clamped 0..1; refuses with 500 when the current volume cannot be read, never steps from a guess), `audio.toggleMute` (`wpctl set-mute @DEFAULT_AUDIO_SINK@ toggle`), `audio.toggleMicMute` (`wpctl set-mute @DEFAULT_AUDIO_SOURCE@ toggle`). `audio.setOutput({ label })` takes a configured output's label (never a sink id from the client): unknown label 404, no matching sink 412.
- playerctl: `--format` does not expand `\t`, so `MEDIA_FORMAT` carries real tabs. "No players found" exits non-zero and is `null` state, not an error.
- Media metadata adds art URL and MPRIS length after the title; parse the trailing fields so title tabs survive. `parseMediaMetadata` is server-only; `parseMediaState` returns nullable lengthMs (microseconds converted to milliseconds) and a 16-character SHA-256 artKey, never the URL. `next`/`previous` use exact playerctl argv through injected run and notify the same hub; errors never forward raw player stderr to clients.
- `modules/media/live.ts` reads position through the selected player's `playerctl position`; seek uses the same preference and validated seconds. When preferred mpv lacks artwork, its `xesam:url` must be a validated YouTube Music watch URL before constructing the server-only thumbnail URL; state and `media.art` share this selection and never expose either URL.
- `modules/media/art.ts` owns one last-cover cache per server, created in the media module's factory. Protected media.art takes no source input, re-reads the current player metadata and accepts only its file: or https: URL. HTTPS uses a 3 s abort signal and refuses redirects; declared and streamed bodies and file reads are capped at 2 MiB. MIME comes from PNG/JPEG/WebP signatures, never an extension/header. Missing, oversized, invalid or unavailable art returns null; errors never expose its source. Tests pass `deps.fetch` to buildServer and never fetch real artwork. No artwork enters SQLite or tracked files.
- Local artwork opens with O_NONBLOCK before descriptor validation; a FIFO with no writer must never occupy a filesystem worker indefinitely. art.test.ts creates only a disposable temporary FIFO and probes it in a child with a hard deadline, alongside regular image/non-image/oversize fixtures.
- Fake media has three generic tracks, a generated geometric fixture (modules/media/fixtures/cover.png, recreated by generate-cover.ts), and next/previous preserve play status. E2E restoration returns both the track and status to their defaults. Real next/previous are never an automated check; smoke only reads metadata/help.

## Live state

Deck tiles update by push, over the tRPC WebSocket (`wsLink` on the client). Polling stays the source of truth on purpose: media keys, the Caelestia popout and Spotify itself change state without going through Hub.

- `createLiveHub(read, intervalMs = 1000)` in `src/core/live.ts` is one poller shared by all subscribers: it reads only while someone is subscribed, compares the JSON with the last value and emits only on change. Pass `null` as the interval for push-only modules such as Pomodoro; it reads only on subscribe and notify. Reads never overlap (a tick or `notify()` that arrives mid-read triggers one more read afterwards, so a state read before a mutation finished is never the last word). A throwing `read` ends the subscriptions with that error instead of crashing the poller, but `read` should not throw on expected conditions (`run` never does).
- A hub's `readOnce` stores nothing once the last subscriber left (`subscribers === 0`): a push-only hub (`intervalMs = null`) would otherwise replay that stale state to the next subscriber. Regression in `live.test.ts`.
- Each stateful module has `src/modules/<module>/live.ts` with `read<Module>State(run, ...)` (the one function behind both the `state` query and the hub) and `create<Module>Live(...)`. Each module's `create` builds its hubs once per server (`buildServer` calls every factory); they are not module-level singletons, so tests with a fake `run` never share state.
- `onState: protectedProcedure.subscription(({ signal }) => live.subscribe(signal))`, with `live` the hub the module's factory built. Always pass `signal`: the generator parks on `events.on(...)` and `return()` on an async generator that is mid-`await` is queued until the next event, so only the abort signal ends an idle subscription (and stops the timer when the last one leaves). The first yield is the current state, then every change; a new subscriber after an idle period reads fresh state instead of replaying a stale one.
- After a mutation succeeds: `void live.notify()`. It is a no-op without subscribers, so HTTP-level tests that assert the last `run` call (`calls.at(-1)`) are unaffected. The new state is pushed, the mutation does not return it.
- Measured on the real stack: a change made in Spotify reached the tile in 0.6 to 0.7 s (it waits for the next 1 s tick). playerctl lags the real change slightly after a mutation, so the immediate refresh can still read the old status; the next tick corrects it.
- Event sources (`pw-mon`, `playerctl --follow`) are a possible later optimisation, not a requirement.

## Config

`loadConfig()` in `src/core/config.ts` reads `$HUB_CONFIG`, default `config.local.json` at the repo root (resolved from `import.meta.url`, not the cwd). A missing file is an empty config; an invalid one throws a message naming the file and the field. Personal values (output labels, device name matches) live there, validated by the zod schema; `server.allowedOrigins` (array, default empty) adds page origins to the WebSocket allowlist; `config.example.json` is tracked with fake values and a test checks it parses. `src/index.ts` loads it and passes it to `buildServer`; procedures read `ctx.config`.

`HUB_PORT` moves both the server and the Vite proxy target, so a second dev stack can run next to one that is already on 4180. `server.host` (default `127.0.0.1`) is where `src/index.ts` listens; `assertCanListen(config)` refuses to start on a host the LAN can reach while `server.allowedOrigins` is empty, because every page would be refused, and its message says which origin to add (for example `http://<pc-name>.local:4180`).

## Settings (Impostazioni)

- An agent reading `settings.config` of a module without a schema gets `null`: nothing marks secrets in a raw slice, so only the PC sees it (`settings-router.test.ts`). `settings.core`/`saveCore` (loopback only) edit the core sections `mcp` and `jobs`, never `server`.
- `core/settings-router.ts` (`settings.*`, mounted by `createAppRouter` next to `registry`, not a `defineModule`) allows loopback and agent clients for `config({ module })`, `save` and `restore`; all other settings procedures stay loopback only. `modules` returns name, `kind` public/private, `status` on/off/failed and `hasConfig`. `modules.enabled` is the one protected query (names of modules that are on, so the deck can hide tiles). `settings` and `modules` are reserved names for discovery.
- **Off is a top-level `modulesOff: string[]`** in the config (`core/config-schema.ts`), never inside a module's slice: slices belong to their own, often strict, schemas. `createAppRouter` does not call `create` for an off public module and mounts `router({})` there (its paths answer `NOT_FOUND`; tRPC cannot answer for procedures nobody knows, owner decision 2026-11-09); `discoverModules` imports the definition but never creates it, opens no database and so leaves `modules/<name>.db` untouched. `core/module-states.ts` (`createModuleStates`) records every module at startup (`on`, `off`, `failed`); a failed one keeps its schema so settings can repair it, and its log line still carries the folder name only.
- **Schema for the form**: `settingsSchema` (optional field of `defineModule`) wins over `config`; a module whose config is absent, `z.undefined()`, `z.unknown()` or `z.any()` has no form, only the switch (`configSchemaOf`). Lavoro accepts any slice in `config` on purpose and names `profileSchema` in `settingsSchema`. `config` returns `z.toJSONSchema(schema, { io: 'input', unrepresentable: 'any' })` (`core/settings-config.ts`).
- **Secrets are write-only**: `.meta({ secret: true })` on a field (it survives into the JSON Schema as `"secret": true`; `secretPaths` finds them at any depth through objects and unions). `config` answers `{ set: true }` for a stored one and lists every secret path in `secrets`; `save` takes `{ set: true }` as "keep the stored value" and a string as a replacement. The value never leaves the server, and a test greps the whole response for it.
- **`save({ module, enabled, value? })`** edits the raw JSON of the file (not the parsed config, so unknown keys survive), validates it with the full `configSchema` and, for a discovered module, with the module's own schema, and answers `{ ok: false, issues: [{ path, message }] }` (path relative to the module's slice) without touching anything, or writes: copy to `<file>.bak`, temporary file with the original mode (owner-only for a new one), rename. `value` is `z.unknown().optional()`: zod 4 makes a bare `z.unknown()` key required, which broke the switch-only save (regression test in `settings.test.ts`). `restore` (danger, `confirmed: true`) swaps the file with `.bak` the same way, 404 without one and 412 when the backup does not parse with `configSchema` (a broken hand edit would otherwise leave the service failing on every restart).
- **Restart**: `ctx.restart()` (a function on the tRPC context, only `save`/`restore` call it) schedules `buildServer`'s `settings.onRestart` for when the response has finished (`res.raw.once('finish')`) and returns whether anything will restart. `index.ts` passes `onRestart` only under systemd (`INVOCATION_ID` set): `app.close()` first (module cleanup runs, a Lavoro collection is cancelled and recorded), then exit code 75 and `hub.service` (`Restart=on-failure`) starts it again, no `deploy/` change. From a terminal (`pnpm dev`, `pnpm serve`) nobody would start it again, so a save only writes the file and answers `restarting: false` (the page says to restart Hub). The e2e fake restarts in place (`apps/e2e/AGENTS.md`).
- Settings `save`, `saveCore` and `restore` run through one promise chain (`serialized` in `core/settings-router.ts`): each is a read-modify-write of the same file, so two at once would lose one change. The temp file name also carries a `randomUUID()`.
- `settings.save`, `settings.restore` and the opted-in query `settings.config` are in `registry.list`. Agent saves and restores refuse the whole change when a secret or `.meta({ manual: true })` field changes, or pairing, devices or health is switched off; human approval does not override this rule. `server.host` is manual. Secrets inside objects, arrays and records are redacted and restored through the schema.
- Tests: `core/settings.test.ts` (paired device refused on every procedure, invalid save changes nothing, valid save keeps `.bak`/mode and asks for one restart, secrets, `settingsSchema`, switch-only save, no restart hook), `server-modules.test.ts` (`modulesOff` of a public module), `core/discovery.test.ts` (off discovered module and its db file, failed module and payload-free log). Never point a settings test at `config.local.json`: they use a `mkdtemp` file.

## Fake desktop and smoke check

- `src/testing/fake-desktop.ts` (`createFakeDesktop({ notifications? })`) is the one fake `Run`: the `pw-dump` fixture with a default sink that `wpctl set-default <id>` moves, sink volume/mute and mic mute simulation for `wpctl get-volume`, `set-volume` and `set-mute`, fake AirPlay service states (`airplay status|start|stop`), and one track (`Artist` / `Title`) whose status flips on `playerctl play-pause`. `notify-send --app-name Hub <title> <body>` is accepted and recorded in the optional notifications array without invoking a binary. Anything else, including an unknown sink id, is answered with a non-zero code and no state change, so it can never reach a real binary (`fake-desktop.test.ts`). Each call makes a new desktop; tests and `fake.ts` share this module, do not write a second fake.
- `src/testing/fake.ts` is the server for the e2e suite: `buildServer` with that fake, an in-memory DB, a fixture config (outputs `Cuffie` and `Casse`, the e2e Vite origins on the allowlist) and an `isLoopback` that treats a request with `Host: localhost:*` as the PC and any other host as a phone. Loopback, port `HUB_PORT` (default 4190). Never point it at a real config. It owns a config file in `HUB_E2E_TMP` for Impostazioni and a file database there (a restart must keep paired devices and module data); `settings.onRestart` closes the server, waits `HUB_E2E_RESTART_MS` (default 1500) and builds it again from the fixture config plus the file (top-level keys of the file replace the fixture's), so no process ever exits.
- `src/smoke.ts` (`pnpm smoke`): `runSmoke(run)` checks `wpctl --help` lists `set-default` (wpctl has no `--version`), `wpctl get-volume` parses sink volume, `playerctl --version`, `pw-dump` through `parsePwDump` (needs a sink and a default sink) and `playerctl metadata` through `parseMediaState` ("No players found" is ok), plus `notify-send --help` for the app-name option (never sends a notification), `pw-play --version`, `systemctl --version`, `caelestia shell -s` (the lock IPC target is listed; nothing is called) and `caelestia toggle --help`, `hyprctl monitors all -j` through `parseMonitorList` (read only; never the toggle), and the powerstat dir through the real parser when `system.powerstatDir` is configured. Read-only by test (`smoke.test.ts` lists the commands it runs); the report says ok, missing or unparseable per check and the exit code is non-zero if any is not ok. `run` returns -1 for both a missing binary and a timeout.
- Smoke also checks `playerctl --player=mpv status` (no player is OK): the `media` module prefers mpv while it is playing or paused (`modules/media/preference.ts`).

## Trust, pairing and the LAN

- **Who is calling** (`resolveClient` in `src/core/auth.ts`, run by `createContext` in `src/server.ts`): `loopback` when the TCP peer address is `127.0.0.1`, `::1` or `::ffff:127.0.0.1` (the PC itself); `device` when `Authorization: Bearer <token>` (HTTP) or the `token` connection param (WebSocket) hashes to a row of `devices`; otherwise `anonymous`. `X-Forwarded-For` is never read and Fastify `trustProxy` stays off: any LAN client can send that header. A `127.0.0.1` peer is always the PC, which is why Vite must never be exposed (its proxy makes everything look like loopback) and the LAN is served by Fastify itself.
- **Procedure kinds** (`src/core/trpc.ts`): `publicProcedure` is for `pairing.redeem` only; `protectedProcedure` (PC, paired device or agent, `UNAUTHORIZED` otherwise) is the default for everything, `health` and every `onState` subscription included; `loopbackProcedure` (PC only, `FORBIDDEN` for a device) is for `pairing.createCode` and `devices.*`. Pick the kind first when adding a procedure; a new one is protected unless there is a reason.
- **WebSocket auth happens once per connection**, when the adapter calls `createContext` with `info.connectionParams` (the client sets `?connectionParams=1` and sends them as its first message). A revoked token therefore does nothing to a socket that is already open: `src/core/auth.ts` keeps `sockets` (device id to open sockets, filled in `createContext`) and `devices.revoke` closes them with code 4401. The adapter passes the `ws` socket where the typings say `FastifyReply`, hence the `isSocket` guard.
- **Pairing** (`modules/devices`: `codes.ts`, `pairing-router.ts`): `createCode` makes one random 6-digit code, valid 120 s, single use, kept in memory (`codes.ts`, one active code, a new one replaces it). `redeem({ code, deviceName })` compares in constant time and returns the token once; a wrong code is `BAD_REQUEST`, and 5 wrong codes per remote address per minute lock that address out with 429 for the rest of the minute, even for the right code. The token is 32 random bytes in base64url; only its SHA-256 is stored (`devices` table: `id`, `name`, `token_hash` unique, `created_at`, `last_seen_at`, refreshed at most once a minute). Revoking deletes the row.
- **The PC switch is an option, not a mode**: `buildServer({ isLoopback })` overrides its default, `isLoopbackPeer` (`core/auth.ts`). Only `src/testing/fake.ts` (the e2e server, which tells the desk page and the deck page apart by `Host`) and tests pass it; `src/index.ts` never does. `core/auth.test.ts` builds the server without the option and pins that `127.0.0.1` is the PC and a LAN address with a forged `X-Forwarded-For` is not.
- **Static app**: `buildServer({ webRoot })` serves `apps/web/dist` with `@fastify/static` and answers extensionless GETs outside `/trpc` with `index.html` (the `/deck` and `/desk` routes); a missing file with an extension, and anything not GET, is a 404. `src/index.ts` passes `webRoot` only when `dist/index.html` exists. `pnpm serve` (root) builds the web app and starts the server.
- **Trying `pnpm serve` without touching real data**: `HUB_DB=<scratch>.db HUB_CONFIG=<missing file> pnpm serve` uses a scratch database and an empty config (the real ones are `~/.local/state/hub/hub.db` and `config.local.json`); pairing writes a device row, so never do it against the real database. The page origin `http://127.0.0.1:4180` is already on the allowlist.

## Database: Drizzle v1 + SQLite (`node:sqlite`)

- One local file, no database server: single user, single writer, small data. Postgres would only earn its place if several machines wrote to the same store.
- Path: `$HUB_DB`, default `~/.local/state/hub/hub.db` (outside the repo). WAL mode and foreign keys are set on open.
- `openDb()` in `src/db/index.ts` applies pending migrations synchronously at startup, before the server listens. Tests use `openDb(':memory:')`. It is `openDatabase(path, migrationsFolder)` with the tracked `drizzle/` folder; the same function opens a module's file (see "Core and module databases"), and closes the handle again when a migration throws.
- Primary keys: `integer` autoincrement for rows that live and die on this machine (sessions, devices, themes). A table whose ids leave it (synced to another store, shown to an agent or a third party, created offline on a device) uses a text UUID from `crypto.randomUUID()` instead, decided when that table is planned.
- Schema in `src/db/schema.ts`, explicit snake_case column names (`integer('started_at', ...)`). Timestamps are `integer` with `mode: 'timestamp_ms'`, booleans `integer` with `mode: 'boolean'`.
- Change the schema, then `pnpm --filter @hub/server db:generate` and commit the folder it writes under `drizzle/`. Never edit a migration that has already run; add a new one. `db:studio` opens Drizzle Studio.
- Drizzle is v1 (release candidate, `drizzle-orm@rc`): the `node-sqlite` driver only exists there. Check the installed typings in `node_modules/drizzle-orm/` before trusting 0.x examples from the web. Relational queries use the v2 object syntax (`where: { id: 1 }`), as in the Efebia projects.
- The core db reaches procedures through the tRPC context (`ctx.db`), never as a module-level singleton.

### Core and module databases

- Two kinds of file. The **core** database (`hub.db`) belongs to the public modules: devices, layouts, themes, Pomodoro history. A **module** database belongs to one discovered module that declared `migrations` in `defineModule`: `<dirname(dbPath)>/modules/<name>.db`, opened by `discoverModules` through `openDatabase(moduleDbPath(dbPath, name), migrations)`, `:memory:` when the core is. It reaches the module only as `deps.db` in its factory, by closure; `ctx.db` is always the core one, and a module's procedures never read it.
- Isolation is by type and by construction: `discoverModules` takes `DiscoveredDeps` (no `db`), `buildServer` passes it a separate object from the public `ModuleDeps`, and a discovered definition with `coreDb` is refused. `defineModule` types `db` from the options: `migrations` gives it, `coreDb: true` gives the core one, neither gives none (`server-modules-db.test.ts` has a `@ts-expect-error` for that). `pomodoro` and `theme` are the two public modules that declare `coreDb`.
- Failures stay local: the database is opened after the name and zone checks and before `create`; if opening, `create` or the instance check throws, the module's `close` and the database handle are closed and the module is skipped.
- Close order: Fastify runs `onClose` hooks last in, first out, so the database hook is registered before the module's `close` and runs after it (a module can still write in `close`; the same reason the core database hook is registered first in `buildServer`).
- Generating a module's migrations is in `docs/modules.md`; `pnpm --filter @hub/server db:generate` is for the core only.
- drizzle names a foreign key `fk_<table>_<column>_<table>_<column>_fk`, which the private-data guard reads as a token. A new migration with a foreign key gets `-- guard-private: allow generated foreign key name` at the end of that line, before its first run (music `playlist_songs`, 23f). `pnpm check` misses it while the folder is untracked; the guard sees it after `git add`.

## HTML for modules

- `linkedom` (exact version in `package.json`) is the one HTML parser, chosen so the server and the browser share a DOM API and one cleaning function can run on both (the Lavoro description cleaner). `core/module-html.ts` re-exports `parseHTML` for module folders, like `module-db.ts` does for drizzle.
- The server tsconfig has no DOM lib: linkedom's declarations reference DOM globals and typecheck here only because `skipLibCheck` is on in `tsconfig.base.json`. A private module is typechecked with the DOM lib (`scripts/tsconfig.modules.json`), where `parseHTML(...).document` is a plain `Document`. Do not import linkedom's `DOMParser`: it returns linkedom's own `HTMLDocument`, which is not assignable to `Document`.
- linkedom's parser is lenient and not spec-exact on malformed markup. Code that must be safe on hostile input builds its output from an allowlist and escaped text instead of editing the parsed tree, and its tests assert properties (only allowlisted tags, no attribute) over a list of hostile strings rather than exact trees.

## Security invariants

- `core/trpc.ts` explicitly sets `isDev: false`: procedure error bodies never include stacks or source paths, regardless of `NODE_ENV` or the service environment.
- WebSocket upgrades (tRPC subscriptions, the deck) check `Origin` against an allowlist before the connection is bound: CORS does not cover WebSockets, so any page open in the browser could otherwise drive the desktop through `localhost`. It lives in `src/server.ts`: `verifyClient` (the 2-argument form, the only one that can answer 403) in the `@fastify/websocket` options, with `isAllowedOrigin` from `src/core/origin.ts`. A missing `Origin` is refused too; a refused upgrade is logged at `warn`. The allowlist is `DEV_ORIGINS` (Vite on 5173, the server on 4180) plus `config.server.allowedOrigins`; trailing slash and case are ignored. Vite on another port (it moves to 5174 when 5173 is taken) is refused until its origin is in the config. HTTP CORS is not configured yet; when it is, it reads the same allowlist.
- `/files` (`core/file-routes.ts`) refuses a request whose `Origin` is present and off the same allowlist: a multipart POST is a CORS simple request with no preflight, so without it any page open on the PC could upload from loopback. tRPC is covered by its `application/json` requirement (415 otherwise). `server-files.test.ts` pins both.
- Fastify `routerOptions.maxParamLength` is 5000 (`server.ts`): tRPC puts a whole HTTP batch in one path parameter, and the default 100 answered 414 once a page batched about 8 calls (Lavoro's initial state broke; `server-batch.test.ts`).
- `@fastify/websocket` must be registered before the tRPC plugin (which gets `useWSS: true` and `keepAlive`), or the WebSocket route is not recognised.
- Who may call what is decided in the tRPC context and three procedure kinds, never inside a procedure body: see "Trust, pairing and the LAN".
- Every LLM call goes through the budget/rate-limit gate in `core/llm-gate.ts` before hitting the provider, so a stuck button or a loop cannot burn the quota.
- Destructive actions (`danger: true` in the meta) are refused with `PRECONDITION_FAILED` unless the input carries `confirmed: true`: `confirmDanger` in `core/trpc.ts` is middleware on the base procedure, so it covers every kind and runs before input validation. Each danger mutation also declares `confirmed: z.literal(true)` so the typed client must pass it; web controls use `HoldButton` or `HoldTile`. `src/router.test.ts` lists every danger mutation and checks each is refused without the flag and runs with it.

## Mail (Posta)

- `modules/mail/`: `himalaya.ts` (argv builders, zod for `--json` answers, plain text of a message), `thread.ts` (`threadOf`, pure), `live.ts` (`readMailState`, `createMailLive`, polled every 60 s only while subscribed), `router.ts`, `config.ts`, `module.ts`. Public module, absent `mail` in config means off: `create` returns an empty router, so no procedure answers and nothing polls.
- Every call is `himalaya --json -a <account> ...` through `ctx.run` with `timeoutMs` 20 s. The account must be in `mail.accounts` (404 otherwise): a name from the client never reaches himalaya unchecked. Hub never reads himalaya's own config, never passes credentials.
- `mail.search` accepts the same validated `mailbox` as `mail.list`, defaulting to `INBOX`; use `sent` to search sent messages. Search filters are joined with AND.
- himalaya answers failures as `{"error": ...}`, and the exit code is 1 in the cases checked; `himalaya()` checks both. A failure is a reason (`timeout`, `failed`, `unreadable`) that the router turns into one short English message: no address, subject or body in it.
- Query words are joined by himalaya and parsed as one string. A value must be double-quoted with `\` and `"` escaped (`quoteValue`), or a space, `and` or `or` in it breaks the parse. `after D` excludes day D, so a window starts the day before (`windowStart`).
- Access: `accounts`, `state`, `onState`, `refresh` and the two flag mutations are `protectedProcedure` (the deck shows the unread count); `list`, `search`, `read` and `threads` are `loopbackProcedure`, so a paired phone never gets what the mail says (owner, 2026-11-09). The `refresh` query notifies the live hub immediately; `accounts` only reads configuration. `state` and `onState` also carry `latest` rows (sender, subject) for the desk widget: `forClient` in `router.ts` empties them for any caller that is not loopback (tests in `router.test.ts` and `core/auth-ws.test.ts`). Any new field with mail content in the state must go through it too.
- Reading never passes `--seen` (the fake refuses it, so a read that sent it fails the test). Flags change only through `setSeen` and `setFlagged`.
- Plain text: `text_body` can point at an HTML part, so text comes from `Text` parts first and falls back to `Html` stripped by `htmlToText` (wrapped in a body first, since a bare fragment has none in linkedom; `head` is never removed).
- Threads join In-Reply-To chains and matching normalized subjects with the same exact counterpart, excluding automated senders. `ThreadView.key` is the smallest listed Message-ID; dedupe only within an account. Null dates and sent calendar replies do not decide waiting.
- The fake (`testing/fake-himalaya.ts`, through `createFakeDesktop({ mail })`) answers the exact argv Hub builds, keeps flags per desktop and refuses anything else. Fixtures are invented (`example.org`).
- Sending (step 39): `compose` and `reply` are `loopbackProcedure` + `danger: true` + `confirmed: z.literal(true)`, so a paired phone, an agent and an unheld call are all refused before himalaya runs. Values reach argv as `--to=`, `--cc=`, `--subject=`, `--body=` (one element each, so a leading `-` is never a flag) and are bounded by `recipientsSchema` (at most 20 `z.email()`), `subjectSchema` (no newline or NUL) and `bodySchema` (at most 20,000 chars, no NUL: execFile throws on one). Always `--send --save sent`. `replyDraft` runs `message reply -m <box> --body= <id> --json` (an explicit empty body: with none himalaya reads stdin, which `run` leaves open) and parses `{ to, cc, bcc, from, subject, body }` (the schema is `himalaya json-schema himalaya-message-reply`; `body` is the quoted text). Send and move answers are not read: `himalayaDone` checks only the exit code and an error payload. Failures are the same generic messages as reads.
- Inbox feed (`feed.ts`, `mail.inbox`): one procedure for one account or all merged, 25 rows a page. The cursor is a count of delivered rows per account, nothing is kept on the server: each call re-reads the pages it needs and hands over a row only when no account with more pages could hold a newer one. A failed account fails the call. `list` and `search` stay as they were (the private Lavoro module uses `search` and `read`).
- Feed sort time (`feed.ts`): each row's merge time is `min(own date, previous row's time)` per account (an undated row takes its predecessor's, or -Infinity when it opens the listing), so delivered rows stay a prefix of each listing, which the per-account count cursor needs. Never sort or bound by the raw `Date`.
- Notifier (`notify.ts`): per account it keeps the newest date seen besides the ids, and notifies only unseen ids newer than it, so an archive that slides an old unread row into the 10-row window stays silent. An undated row has nothing to compare and notifies by id alone.
- Archive: `archive` moves INBOX to `mail.archiveMailbox` (default `archive`, a himalaya alias, same for every account) with `message move -f INBOX -t <box> <id>`; the moved message gets a new id, so `unarchive` finds it again by Message-ID among the archive's listing for its subject (newest page only when the subject is empty) and moves it back. An alias himalaya refuses is one generic error and nothing moves. Neither is `danger`; both are loopback registry actions.
- Notifications (`notify.ts`): config `mail.notify` (default true) keeps one internal subscriber of the live hub from module start to `close`, so the inboxes are polled every minute with no page open (the fake e2e server does too). ## MCP agents

- `core/mcp.ts` serves stateless Streamable HTTP at `/mcp` when `mcp.enabled` is true. An absent Origin is accepted; a present Origin must match the WebSocket allowlist. LAN requests need an agent bearer token. `core/agents-router.ts` issues it once and stores its SHA-256 hash.

- Studio has several active plans at once (plan 40, decision 15): `activeHeaders` lists them, subjects are keyed `<plan>:<subject>` (states, shares) and days `<plan>/<day>` (`daysById` takes these keys), because two plans may share ids such as `C01`. The mix and weekly hours live in the `preferences` row `*`, not per plan; a stored mix that misses an active subject is set aside for equal shares rather than hiding that subject's days. `savePlan` never deactivates other plans; `setPlan` pauses or resumes one.
- Study error log (`modules/study/errors.ts`): entries are `progress` rows of kind `error` (id uuid, JSON value), keyed by plan like every other progress record, so no migration and the `removed` list of the state file ignores them; `study.review` computes Ripasso (red and yellow threads, half-done days) server-side and parses every active day per request (shortcut, fine for hundreds of days). `setError` has a palette label, so `router.test.ts` and `router-registry.test.ts` counts include it.
- Music volume is mpv's own `volume` property: `music.setVolume` (zod int 0..100, `schedule`d, 503 on IPC failure) sets it, `music.state` reports `volume` (null when mpv is unreachable). mpv allows up to 130 (`--volume-max`) but Hub's slider is 0..100. The system volume stays in the `audio` module. Fakes (`music/test-wiring.ts`, `testing/fake.ts`) keep a volume; e2e `restoreDesktop` resets it to 100.
- `node:test` runs `t.after` hooks in registration order. Register the server's close before removing its temp folder, or in one hook (`await app.close(); await rm(...)`): the study tests removed the folder first and failed with ENOTEMPTY under load while the state writer still wrote.
- `llmGate(cap, call, { minIntervalMs, counted })`: `counted: false` (the private Lavoro mail check, step 51) queues and times out like any call but neither meets the cap nor adds to the daily count the Parere shares, so reading a week of mail cannot starve it. `mail/router.ts` exports `listThreadEntries` and `windowStart` for that reader; a private module imports them by relative path.

- Notes (step 38, `modules/notes/`): built-in `coreDb` module, table `notes` in the core schema (text UUID ids because agents see them). `forDay` is a plain local `YYYY-MM-DD` the client sends (the server's own today only fills a missing one, `localDay` in `notes.ts`); "what is due today" is decided in the web app, so a day change needs no server timer. `source` is `desk` or `agent:<name>` from `ctx.client` (`Locale` for the loopback MCP). Remove sets `removedAt`; `restore` clears it. The `notes` name is taken: a test fixture or private module must not use it (the module-db tests use `memo`).
