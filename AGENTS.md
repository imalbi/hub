# AGENTS.md

Hub is a personal control center: one Fastify server on the desktop (CachyOS, Hyprland + Caelestia) exposes a registry of actions to two React clients, `/desk` (dashboard in the `special:hub` workspace) and `/deck` (Stream Deck style PWA on an old iPhone). Design doc (private): https://claude.ai/artifact/EoUAnyrHmvFALAseJp25Cy

## Commands

```bash
pnpm dev          # server on 127.0.0.1:4180 + Vite (proxies /trpc to the server)
pnpm typecheck    # tsc in every workspace
pnpm test         # node:test via scripts/run-tests.ts (cross-platform globs, fails on 0 tests)
pnpm guard        # scan tracked files and modules for private data; see staged-mode note below
pnpm lint         # oxlint --type-aware --deny-warnings + pure-Node scripts/lint-tokens.ts
pnpm format       # prettier --write (format:check to verify)
pnpm check        # guard + typecheck + private-module checks + lint + format:check + test: fast, run while working
pnpm check:modules [name]  # Prettier, tests, tsc, and oxlint (--deny-warnings) for private modules
pnpm verify       # check + e2e + web build: the completion gate also refreshes the served UI
pnpm test:e2e     # Playwright against the fake server (apps/e2e): builds each variant once, then a queue of public (3 shards), example (2) and private jobs on 3 slots (cap 4); lock between sessions; ends with an EXIT line
pnpm test:e2e:private [name] # Playwright against private module e2e with fake desktop (already part of test:e2e; this one runs it alone, one module or all)
pnpm test:e2e:update  # rewrite screenshot baselines: only for an intended visual change
pnpm smoke        # read-only check that the real audio/media tools and notify-send help still parse
pnpm serve        # build the web app, then serve it and the API from the server (no Vite, no watch)
pnpm desktop:install # preview desktop integration; --apply installs, --uninstall previews removal
pnpm --filter @hub/server <script>
pnpm --filter @hub/web <script>
```

Node >= 24, pnpm workspaces, TypeScript 7. Linting is oxlint, not ESLint: typescript-eslint only supports TypeScript up to 6.0, while oxlint's type-aware rules run on `oxlint-tsgolint`, built on the same Go compiler as TypeScript 7. Config in `.oxlintrc.json`; Prettier (with the Tailwind class sorter) in `.prettierrc.json`.

## Layout

- `apps/server` (`@hub/server`): Fastify 5 + tRPC 11 + zod. Runs TypeScript directly with Node type stripping, no build step. See `apps/server/AGENTS.md`.
- `apps/web` (`@hub/web`): React 19 + Vite + TanStack Query + tRPC client + Tailwind v4. See `apps/web/AGENTS.md`.
- `apps/e2e` (`@hub/e2e`): Playwright specs and screenshot baselines against a fake server. See `apps/e2e/AGENTS.md`.
- `deploy/`: desktop templates and installer, no personal values. See `deploy/AGENTS.md`. Deployment TypeScript shares the server's Node typecheck; root `pnpm test` also runs its tests.
- The Hue Bluetooth light and AirPlay controls are self-contained private modules in `modules.local/` (`hue` and `airplay`); `modules.example/hello/` is the sole example module in `hub`. Discovered modules can import `@trpc/tanstack-react-query` and `@tanstack/react-router` by bare name via `apps/web/vite.config.ts` and `scripts/tsconfig.modules.json`. <!-- guard-private: allow Repository-local module directory -->
- `scripts/`: repository checks, included in the server's Node typecheck and root tests. Its local tsconfig reuses the server's Node typings so oxlint also checks it. `guard-private.ts` reads Git snapshots and `guard-commits.ts` checks commit messages; `private-scanner.ts` is the pure detector and returns masked findings only. `run-tests.ts` and `lint-tokens.ts` keep test globs and token lint cross-platform with no external `rg` binary.
- `.github/workflows/ci.yml` and `.github/dependabot.yml`: GitHub Actions CI (`push` on `main`, `pull_request`, and `workflow_dispatch`; `guard` and `check` run automatically, while functional `e2e` runs only on manual `workflow_dispatch` using `pnpm test:e2e` with `HUB_E2E_SKIP_VISUAL=1` excluding `*.visual.spec.ts` plus `ignoreSnapshots: true`, and `HUB_E2E_WORKERS=2`) plus weekly Dependabot checks, with every action pinned to a verified 40-char commit SHA, top-level `permissions: { contents: read }`, and `.gitattributes` enforcing LF text and binary markers.
- End-to-end types: the web app imports `type AppRouter` from `@hub/server`. Never import runtime code from the server into the web app, only types.

## Writing a module

A module is one folder with `server.ts` (`defineModule`, required) and `ui.tsx` (`ModuleUI`, optional): public ones in `apps/server/src/modules/<name>/` listed in `apps/server/src/modules.ts`, local and catalog-installed ones in the gitignored `modules.local/` and `modules.installed/` (`defaultModuleRoots`, with `modules.local/` winning on collision; cloned Git catalogs live in `modules.repos/`), discovered at startup. Shared server packages come through the re-exports in `apps/server/src/core/` (`module.ts`, `module-db.ts`, `module-html.ts`); a module may own additional npm dependencies through its own `package.json` and `pnpm-lock.yaml` (see `docs/modules.md`). `modules.example/hello/` is the working reference. <!-- guard-private: allow Repository-local module directory -->

**Before writing or changing a module, read `docs/modules.md`**: config, storage and migrations, files, HTML, web zones and sections, discovery points, checks and private e2e.

## Hard rules

- **Public repo, private life stays out.** The repo is public (showcase, all rights reserved). No home paths, hostnames, IPs, device names, tokens or personal data in tracked files. Personal modules live in the gitignored `modules.local/`; personal values in the gitignored `config.local.json`, with a fake `config.example.json` tracked. If a change needs a personal value, read it from config, never hardcode it. `pnpm guard` enforces built-in patterns and an optional gitignored `.private-words` list; only the owner fills that list. Never open or print it. <!-- guard-private: allow Repository-local module directory -->
- **Only registry actions run.** The server never executes arbitrary shell commands, not even when an LLM asks. Every side effect is an action with a zod-validated input. Spawn binaries with an argument array (`execFile`), never a shell string.
- **Never read secrets.** Do not open, cat or print `.env*` or `config.local.json`.
- **Loopback unless paired.** The server binds `127.0.0.1` by default. `server.host` in the config can open it to the LAN, and then only a PC (loopback) or a paired device token gets past `protectedProcedure` (see "Trust, pairing and the LAN" in `apps/server/AGENTS.md`). Never bind to the LAN or edit the real config yourself: the owner does that.
- **Desktop install is opt-in.** `pnpm desktop:install` never writes or starts services without `--apply`; removal needs `--uninstall --apply`. Only the owner applies on the real desktop. The active Hyprland configuration uses Lua: edit the managed block in `hypr-user.lua`, never the legacy `hypr-user.conf`.

## Code style

- English for identifiers, files, comments and commit messages. UI copy is Italian only, through Paraglide (see `apps/web/AGENTS.md`).
- No `any`, no `dangerouslySetInnerHTML` (`react/no-danger: error`, unless sanitized and justified by a scoped `oxlint-disable`), and no `as` assertions unless unavoidable, each one justified by a short comment. Never `as unknown as`: fix the source type, add a type guard or parse with zod. Vendored `apps/web/src/components/ui/**` tolerates upstream warnings via an `overrides` entry in `.oxlintrc.json`.
- No IIFEs; extract a named function.
- No em-dashes and no filler phrasing in UI copy, README or commit messages. No emoji.
- Prefer the platform and what is already installed over a new dependency; ask before adding one that only saves a few lines.
- Before writing or vendoring a non-trivial component (an animation primitive, a widget, anything past ~100 lines), list maintained libraries that already do it, with size, maintenance and fit, and let the owner choose: owning it versus a dependency is their call, not the agent's.
- Comment only the why the code cannot show.

## Workflow

- Start a step with `pnpm step:start <step> <name>` in one network-enabled call; it checks clean trees, pulls discovered repos, and commits/pushes only the plan claim. Use `pnpm step:status` for an offline multi-repo summary. Omit the name only to sync and inspect without claiming; source commits remain the reviewer's responsibility.
- Read `plans/VISION.md` (the project's purpose and principles) before planning or executing. Work arrives as a plan file in `plans/` (gitignored by `hub`, versioned in its own private repo `hub-plans`). Follow it: do not reopen decisions it records as taken; if one turns out wrong, stop and say so instead of improvising. A step is done only when its acceptance criteria are met. Keep the plan's `## Progress` checklist current as you go (tick + one-line note per item), so another agent can resume from it and `git diff` if the session stops. **Every handoff writes forward:** before calling a step done, append a `## Handoff from step NN` section to the next plan file (create a stub with just that section if the next plan does not exist yet): what now exists that the next step builds on (names, files, context shape), deviations from the plan and why, gotchas found, limits left open. The reviewing session adds its own review notes there too.
- Executors do not use plugin workflows that manage plans, worktrees, commits or reviewers (for example superpowers' executing-plans, subagent-driven-development, using-git-worktrees, finishing-a-development-branch): this file's workflow applies. A worktree would also leave out the ignored `modules.local/`. Skills that only reinforce it, such as test-driven development and systematic debugging, are fine. <!-- guard-private: allow Repository-local module directory -->
- **Keep plans executable.** Before a step, compare its prerequisites and named APIs with the current code/tests and the latest handoffs; record the checked commit, existing work and unresolved conflicts in the plan. Correct stale facts without reopening approved decisions; stop on a decision conflict. At handoff, update `plans/README.md` and the instructions/acceptance in affected future plans too, so an old instruction cannot undo shipped work. Anything a plan leaves to "a later step" or "its own plan" must land in that plan, or in `plans/BACKLOG.md` when the plan does not exist yet; a rewrite of a plan keeps or explicitly drops what earlier plans left to it. Keep historical notes labelled as history; never mark future checks passed from an earlier run.
- **Settle from the code, stop only on decisions.** A doubt the code or tests answer (an ambiguous rule, a stale path, a line the code contradicts) is not a reason to stop: correct it, note in Progress the file and line that settle it, and continue. Stop and ask only on a conflict with a decision the plan records, or on a choice that is the owner's.
- Library and system APIs are checked before use, not recalled: Context7 for docs (TanStack, tRPC, Fastify, Tailwind), the installed source in `node_modules` or `/usr` for behaviour, `--help` for CLIs (`wpctl`, `playerctl`, `hyprctl`, `caelestia`).
- **Several developers, one public and two private repos.** `hub` (public root), `hub-local` (private) cloned into `modules.local/` and `hub-plans` (private) cloned into `plans/`; setup in `docs/onboarding.md`. Before a step, `git pull --rebase` in all three; if a pull conflicts, stop and ask. <!-- guard-private: allow Repository-local module directory -->
- **Claim before starting.** A step is taken by writing `taken by <name>, <date>` in its row of `plans/README.md` and pushing `hub-plans` at once; a step already claimed by someone else is not started. Steps that edit the same files (every Lavoro source step touches `config.ts` and `server.ts`) never run in parallel, even under different owners.
- Start a step from a clean tree; executors never commit or push; the reviewing session makes one commit per step after review, then pushes the repos it touched (`hub`, `hub-local`, `hub-plans` for plan updates) and clears the claim. Never force-push `main`, never rewrite pushed history. At the end of a step, after `pnpm check` is green, stage everything with `git add -A` and check the staged file list for anything that must not be tracked. The guard runs in the hook; still read the staged list. Details in `plans/README.md`. No `Co-Authored-By` or session trailers.
- UI changes are not done until checked in a real browser (desk at 4K, deck at 375x812).
- **A plan that names an approved mockup is checked against it live, by the executor and again by the reviewer.**
  - Open the board (Artifact tool `read`, or its local copy) and render it at the same viewport as the page.
  - Screenshot both, view them side by side, and walk the board element by element: layout and proportions, order, grouping, what floats and where, borders, counts and copy.
  - The desk root is 150%, so built px are 1.5x the board's.
  - Every difference is either fixed or written in the plan as a deviation for the owner to accept.
  - A report that says "matches the mockup" without that walk is not a check: the reviewer redoes it, never trusting it. Two shell slices passed review that way while the rail and the Musica player did not match their boards (2026-11-13).
- Design references live in the private project reference library; ask the owner for access and read each reference note before using it.

## Verification and tests

- `pnpm demo` uses `scripts/demo.ts` with fresh temporary storage, empty module roots for both server and Vite, and an empty served-build root. Keep these overrides together: otherwise an inherited module root or existing `dist` can expose personal UI in the fake demo.

Nothing is done until it is verified, and nothing verified once stays unguarded.

- **Every planned change ships with its checks.** A plan's Acceptance lists the tests to add by behaviour (not "add tests") and the manual or visual checks to make. The executor records in the plan's Progress notes what each check actually showed.
- **Where tests go:**
  - pure logic (parsers, pickers, state reducers) gets unit tests next to the code (`*.test.ts`, `node:test`); the shared VS Code settings (`.vscode/settings.json`) fold each test under its source file in the explorer, so they add no noise. Name a test after the file it covers: `x.test.ts`, or `x-<aspect>.test.ts` for a second suite (`server-live.test.ts` under `server.ts`); a test with no matching file shows loose;
  - server behaviour gets integration tests through `buildServer(...).inject` with a fake `run` and fixture config;
  - UI behaviour and layout get e2e specs and screenshot baselines in `apps/e2e` (Playwright against the fake server, see `apps/e2e/AGENTS.md`). A UI change ships with its spec: assert by role and accessible name, and add or update the baseline only when the look change is intended.
- **Tests never touch the real desktop or personal data.** System commands go through an injected fake; fixtures use generic device names. The only exception is `pnpm smoke`, which is read-only by design.
- **Node test output under the workspace sandbox.** If `node --test` reports only one implicit file-level result, pass or failure, and no named subtests, the sandbox may have blocked the test runner's IPC. Treat that as inconclusive; rerun fixture-only checks outside the sandbox with approval/escalation instead of changing the tests or runner.
- **Every bug gets a regression test first**: write the test that fails on the bug, then fix it, and keep the test.
- **Never weaken a test to get green.** Do not delete, skip or loosen a failing test, and do not update screenshot baselines, unless the change in behaviour or look is intended; say which and why in the Progress notes.
- **The gate:** `pnpm check` while working; `pnpm verify` (check + e2e + web build) before a step is called done. The final build refreshes `apps/web/dist`, served by the installed service, only after all checks pass; this is authorized at step completion and needs no separate rebuild request. It does not restart the backend or apply desktop integration. The pre-commit hook (`.githooks/pre-commit`, set up by the root `prepare` script on `pnpm install`) runs the staged guard, refuses unstaged tracked edits or untracked files before running `pnpm verify` (outside `.md`-only and exact-tree stamp fast paths), and is paired with `.githooks/commit-msg` and `.githooks/pre-push` (`scripts/guard-commits.ts`) to scan commit messages and unpushed commits. `scripts/verify.ts` compares `worktreeTree()` at start and finish (`scripts/verify-stamp.ts`) and refuses to stamp if the worktree changed mid-run. A green verify ends by stamping the tree it tested (stored in the git dir), and the hook skips the full gate only when the index is exactly that tree (a commit right after the executor's or reviewer's verify) or when every staged path, old names of renames included, ends in `.md` (then it runs the guard and Prettier on them). Anything else, even one changed file, runs it in full. The stamp does not see dependency or system changes outside the tree: after `pnpm install` or a system update, run `pnpm verify` again before committing; `--no-verify` only with the user's explicit OK or for a one-module step ("Full verify by reach" below).
- **Parallel e2e, and what it asks of specs:** `pnpm test:e2e` (`scripts/test-e2e.ts`) builds each e2e variant once, then runs a queue of jobs (public pass in 3 file-balanced shards, example in 2, each private module, plus one dev-server job) on `WORKERS` slots (4 since 2026-11-16: the queue went from 283 s to 257 s, and the longest single job, the Lavoro private pass at about 4 minutes, is now the floor; the owner's OK is up to 4 processes, never more without asking again). Each process has its own fake desktop, free ports and temp folder (`apps/e2e/tests/hosts.ts`, details in `apps/e2e/AGENTS.md`). Never hardcode a port or a `/tmp/hub-e2e-*` path in a spec or the fake server; import the constants. A lock in the git dir (`hub-e2e-lock`) makes a second session's run wait instead of stacking processes. `pnpm test:e2e:update` stays serial.
- **Per-target verification cache:** `check`, module checks and e2e variants reuse input-hashed passes in `.git/hub-pass-stamps.json`; inputs are rehashed after success and drift prevents stamping. Visual and `HUB_E2E_SKIP_VISUAL=1` passes are separate. Custom `HUB_MODULES_ROOT` runs, staged `check` and module `--write` bypass caching. Use `HUB_VERIFY_NO_CACHE=1` after dependency or system changes, or to force every check; successful forced runs refresh stamps. The hook still runs its staged guard.
- **One full gate per step.** `pnpm verify` runs once, after the review and its fixes, with no edits while it runs. Before it: targeted specs while working (`pnpm --filter @hub/e2e e2e <file>.spec.ts`), then `pnpm check` (about 15 s). A failing verify that `pnpm check` would have caught, or one run before the review, is wasted time (step 12 spent four full runs). With a separate reviewer, the executor hands off after `pnpm check` and its targeted specs, baselines included, and does not run the full verify. The reviewer runs the one verify after the review fixes. If the review needs no fixes, the verify runs on the tree as handed off. Two exceptions:
  - The executor still runs the full verify itself when it touched shared pieces (the shell, `Panel`, `PageSurface`, `ZoneTabs`, tokens in `index.css`, a shared hook), because those can break pages it did not test.
  - When the reviewer's verify fails on something the review fixes did not touch, the reviewer sends it back to the same executor (it keeps its context) and runs the verify again after its fix, instead of debugging it.
- **Full verify by reach, not by step (owner, 2026-11-16).** A step that stays inside one module (its folder, its own specs and messages, no shared piece listed above, no shared baseline) closes after the review with `pnpm check`, that module's specs in every pass that loads it (public, example, private: `pnpm test:e2e:private <name>` for a private one) and `pnpm --filter @hub/web build` so the served app updates; its commit uses `--no-verify`, which the owner allows for this case only. A step that touches a shared piece or a shared baseline runs the full `pnpm verify` as above. Nothing is pushed without a green full `pnpm verify` on the tree being pushed, so the remote never holds an unverified commit. An executor whose step changes a baseline runs that spec in the example pass too (`HUB_EXAMPLE_MODULES=1`): step 70's verify failed there after the public pass alone was run.
- **Wait for long commands inside Code Mode, do not poll from the model.** For `pnpm verify`, `pnpm test:e2e` and `pnpm check`, follow the executable JavaScript example in the global Codex `AGENTS.md`: set the outer `// @exec: {"yield_time_ms": 600000}` pragma and await `write_stdin` in a JavaScript loop until the process exits. Save full output to a distinct local log and preserve the exit code; read counts/failures after completion. If `exec` yields a cell ID, resume that same cell with `functions.wait`, without starting another shell poll. Never loop over log files or return to the model every minute for progress. The final `EXIT <code>` line is the completion signal; periodic commentary alone is not a reason to shorten waits.
- **Private-data guard:** manual guard/check/verify scan every tracked worktree file; the pre-commit hook exports `HUB_GUARD_STAGED=1` so the same guard reads only staged blobs, including partially staged files. `HUB_GUARD_STAGED=1 pnpm guard --staged` selects that mode explicitly for both scanners: the root script chains two commands, so a trailing argument alone reaches only the second. Detection covers IPv6 ULA/link-local, CGNAT/link-local IPv4, private local DNS suffixes, BlueZ/dotted/colon/dash MACs, Windows and POSIX home paths, hint-free secret prefixes and credential hints, Italian phone/IBAN/codice fiscale, obfuscated `.private-words` variants (never waived by `guard-private: allow`), file paths, commit messages, and PNG `tEXt`/`iTXt`/`zTXt` chunks; binary detection checks the first 8 KiB, leaf symlinks are scanned as link text, and symlinked parent directories are refused before opening a file. Accidentally tracked config/secret files and tracked files under `apps/e2e/__screenshots__/private/` fail immediately (private Playwright snapshots live under `modules.local/<module>/e2e/__screenshots__`). Deliberate generic matches need a trailing `//`, `#`, `--`, HTML or CSS `/* */` comment `guard-private: allow <reason>` on the same line; use documentation IP ranges in fixtures. Guard failures report masked matches, not source lines. This heuristic does not inspect pixel contents or rewrite history. <!-- guard-private: allow Repository-local module directory -->
- `scripts/check-modules.ts` passes explicit source files to oxlint: installed catalog folders are gitignored, so the normal lint discovery would skip them. The ignored-root regression also requires real lint errors to fail.
- **System drift:** `pnpm smoke` (`apps/server/src/smoke.ts`) runs only read-only commands on the real machine, feeds them through the real parsers and exits non-zero when a binary is missing or its output no longer parses. It is not part of `pnpm verify`. Run it after system updates and whenever a module that wraps a system tool changes; a new wrapped tool gets a check there.

## Keeping these files current

`AGENTS.md` is the single source of rules for every agent (Claude Code, Codex, opencode, Antigravity); each `CLAUDE.md` only imports it with `@AGENTS.md`. Edit `AGENTS.md`, never the `CLAUDE.md` stubs.

When work introduces or reveals a non-obvious pattern, invariant, gotcha or decision, update the relevant AGENTS.md before ending the task, without asking. Terse bullets with file paths and the why; delete entries that become wrong. Put a module note in its own `AGENTS.md` (create it with a `CLAUDE.md` stub when missing), an app-wide note in the app file, and a cross-cutting rule in this root file. Do not duplicate what git log or the code already says.
